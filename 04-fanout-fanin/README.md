# 04 · 팬아웃-팬인 (Fan-out / Fan-in)

> **한 줄로**: 여러 명에게 **동시에** 같은 일을 뿌리고(팬아웃), 결과를 하나로 모으는(팬인) 패턴.

## 바로 실행하기

```bash
cd 04-fanout-fanin

# 리뷰어 4인이 동시에 리뷰
opencode run "/review-file sample/login.js"

# 비교용 — 한 명만 돌려 보기
opencode run "/review-one sample/login.js"

# 현재 git 변경분 리뷰
opencode run "/review"
```

**`/review-one` 을 먼저 돌려 보고 `/review-file` 을 돌려 보세요.** 한 명과 네 명의 차이가 이 샘플의 전부입니다.

## 무엇을 보여주는 샘플인가

같은 파일 하나를 **관점이 다른 네 명이 동시에** 봅니다.

| 리뷰어 | 보는 것 | 모델 | 왜 이 모델인가 |
|---|---|---|---|
| `review-correctness` | 로직 버그, 경계 조건 | 무난 | 판단이 필요 |
| `review-security` | 취약점 | **고가** | 놓치면 가장 비쌈 |
| `review-readability` | 이름, 구조, 매직 넘버 | 저렴 | 기계적인 확인 |
| `review-tests` | 테스트 유무와 실질 | 무난 | 판단이 필요 |

`sample/login.js` 에는 **네 관점에 각각 걸리는 결함**이 일부러 심어져 있습니다. 한 명만 돌리면 자기 관점의 것만 잡아냅니다.

## 패턴이 보이는 지점

### ① 한 응답 안에서 네 번 호출한다

`.opencode/agents/review-lead.md`:

> **한 번의 응답 안에서 네 개의 `task` 를 모두 호출하세요.**
> 하나 부르고 결과를 기다렸다가 다음을 부르면 팬아웃이 아닙니다. 시간이 4배로 늘어납니다.

이게 팬아웃의 전부입니다. 순차 호출과 병렬 호출의 차이는 **호출을 한 턴에 몰아넣느냐**뿐입니다.

### ② 관점을 프롬프트가 아니라 에이전트에 넣었다

오케스트레이터가 네 명에게 보내는 프롬프트는 **전부 같습니다.** "보안을 봐라" 같은 지시를 덧붙이지 않습니다. 관점은 각 리뷰어의 시스템 프롬프트에 이미 박혀 있기 때문입니다.

덕분에 리뷰어를 하나 추가해도 **오케스트레이터를 고칠 일이 거의 없습니다.**

### ③ "보지 않을 것"을 명시했다

각 리뷰어에는 `## 당신이 보지 않는 것` 절이 있습니다.

> 다른 관점은 **다른 리뷰어가 따로 봅니다.** 남의 영역까지 지적하면 리포트가 중복되고 길어집니다.
> 당신의 관점에서 할 말이 없으면 "없음"이라고 쓰는 것이 정답입니다.

팬아웃이 실패하는 흔한 방식이 **전원이 같은 말을 하는 것**입니다. 넷을 띄웠는데 넷 다 "이름이 이상하다"고 하면 한 명 띄운 것과 다를 게 없습니다.

### ④ 출력 형식을 고정해 취합을 가능하게 했다

네 명 모두 `## 판정` / `## 발견` / `## 차단 사유` 로만 답합니다.

위임 결과는 **마지막 텍스트 한 덩어리**로만 올라옵니다. 형식이 제각각이면 오케스트레이터가 취합할 방법이 없습니다. **팬인은 형식 합의에서 시작합니다.**

### ⑤ 판정은 만장일치, 불합격은 한 명이면 충분

> **하나라도 FAIL 이면 전체 FAIL 입니다. 다수결이 아닙니다.**

보안 리뷰어 혼자 BLOCKER를 냈는데 나머지 셋이 PASS라고 다수결로 통과시키면, 관점을 나눈 의미가 사라집니다.

### ⑥ 리뷰어는 아무것도 고칠 수 없다

넷 다 `edit: deny` 이고, `bash` 도 git 조회 명령만 열려 있습니다.

```yaml
bash:
  "*": deny
  "git diff*": allow
  "git log*": allow
  "git status": allow
  "git show*": allow
```

`bash` 를 통째로 막지 않고 **패턴별로 열어 둔** 예시이기도 합니다. 리뷰에는 변경 이력이 필요하지만, 파일을 지우거나 설치하는 것은 필요 없습니다.

### ⑦ 취합자도 편집 권한이 없다

`opencode.jsonc` 의 전역 기본값부터 `"edit": "deny"` 입니다. 이 샘플은 **읽고 판정만** 하는 것이 목적이므로, 오케스트레이터조차 코드를 못 고칩니다.

## 직접 바꿔 보기

- **`/review-one` 과 `/review-file` 을 비교하세요.** 한 명이 놓친 것을 나머지 셋이 잡아내는 걸 눈으로 확인할 수 있습니다.
- **리뷰어 하나를 빼 보세요.** `review-security.md` 를 다른 이름으로 바꿔 두고(예: `.bak`) 돌리면 보안 결함이 통째로 리포트에서 사라집니다.
- **오케스트레이터에게 순차 호출을 시켜 보세요.** `review-lead.md` 의 "한 응답 안에서" 지시를 "한 명씩 순서대로"로 바꾸면 걸리는 시간 차이를 체감할 수 있습니다.
- **BLOCKER 기준을 바꿔 보세요.** 각 리뷰어의 심각도 기준에서 "실제로 문제가 생긴다를 설명할 수 있을 때만"을 지우면 BLOCKER가 남발되기 시작합니다.
- **다섯 번째 리뷰어를 추가해 보세요.** 예: `review-performance.md`. 오케스트레이터의 호출 목록에 한 줄만 추가하면 됩니다.
- **자기 코드에 써 보세요.** 다른 프로젝트에서 이 폴더의 `.opencode/` 를 복사해 넣고 `/review` 를 돌리면 실제 변경분을 4인 리뷰할 수 있습니다.

## 파일 구조

```
04-fanout-fanin/
├── opencode.jsonc
├── .opencode/
│   ├── agents/
│   │   ├── review-lead.md          취합자 (primary) ← 동시 호출 지시가 여기
│   │   ├── review-correctness.md   정확성 (무난)
│   │   ├── review-security.md      보안 (고가)
│   │   ├── review-readability.md   가독성 (저렴)
│   │   └── review-tests.md         테스트 (무난)
│   └── commands/
│       ├── review-file.md          /review-file  — 파일 하나, 4인
│       ├── review.md               /review       — git 변경분, 4인
│       └── review-one.md           /review-one   — 비교용, 1인
└── sample/
    └── login.js                    네 관점에 각각 걸리는 결함을 심은 파일
```
