# 06 · 조합 · 경쟁형 (Compete)

> **한 줄로**: 같은 문제를 **여러 명이 서로 다른 방식으로** 풀게 하고, **실제로 돌려서** 승자를 뽑는 조합.

## 바로 실행하기

```bash
cd 06-combined-compete

# 버그가 진짜인지 재현만 먼저 (권장)
opencode run "/repro-only"

# 전체 — 재현 → 3인 경쟁 → 실행 채점 → 승자 반영
opencode run "/fix"

# 중간에 끊겼을 때 이어서 보기
opencode run "/status"
```

## 무엇을 보여주는 샘플인가

`sample/parser.js` 에 진짜 버그가 하나 있습니다. `"1h30m"` 을 90분으로 바꿔야 하는데 **6030** 이 나옵니다.

이 버그를 **세 명이 동시에, 각자 다른 접근으로** 고칩니다.

| 후보 | 접근 방향 |
|---|---|
| a | **최소 수정** — 가장 적은 줄을 바꿔 증상을 없앤다 |
| b | **입력 검증 강화** — 잘못된 값이 들어오는 지점에서 막는다 |
| c | **구조 개선** — 이 버그가 생길 수 없는 구조로 바꾼다 |

그리고 심사위원이 **셋을 전부 실행해서** 채점합니다. 토론이 아니라 실행 결과로 정합니다.

## 조합된 패턴

| Phase | 담당 | 패턴 | 모델 |
|---|---|---|---|
| 1 재현 | `reproducer` | **생성-검증**의 앞단 — 판정 기준을 먼저 만든다 | 저렴 |
| 2 경쟁 | `challenger` ×3 | **팬아웃** — 단, 같은 일을 다르게 | 무난 |
| 3 심사 | `judge` | **팬인 + 생성-검증** — 실행해서 채점 | 고가 |
| 4 반영 | `finisher` | 파이프라인 마무리 | 무난 |

## 패턴이 보이는 지점

### ① 판정 기준을 **가장 먼저** 만든다

Phase 1이 하는 일은 고치는 게 아니라 **`_workspace/1-repro.js` 를 만드는 것**입니다.
이 스크립트의 종료 코드가 이후 모든 채점의 기준이 됩니다.

> **재현 없이 수정 금지** — `1-repro.js` 가 실제로 실패하는 걸 확인하기 전에 Phase 2로 가지 않습니다.

재현되지 않는 버그를 고치면 **고쳐졌는지 알 수 없습니다.** 이 순서가 핵심입니다.

### ② 팬아웃인데 지시가 서로 다르다

04의 팬아웃은 **관점**이 달랐고(정확성/보안/…), 여기서는 **해법의 방향**이 다릅니다.

`compete-lead.md` 를 보면 셋에게 각각 다른 `접근 방향:` 을 줍니다.

> 접근 방향을 다르게 주는 것이 **이 샘플의 핵심**입니다. 같은 지시를 주면 셋이 같은 답을 냅니다.

### ③ 병렬 편집 충돌을 사본으로 푼다

셋이 동시에 `sample/parser.js` 를 고치면 서로를 덮어씁니다. 그래서:

```bash
cp sample/parser.js _workspace/2-candidate-a.js   # 각자 자기 사본
```

그리고 재현 스크립트가 `TARGET` 환경변수로 대상을 바꿀 수 있게 만들어 뒀습니다.

```bash
TARGET=_workspace/2-candidate-a.js node _workspace/1-repro.js
```

이게 **git worktree 없이 병렬 편집을 안전하게 만드는 가장 싼 방법**입니다.

### ④ 심사는 실행 결과로만 한다

`judge.md`:

> **보고서를 믿지 마세요. 직접 돌리세요.**
> 후보의 자기 보고를 근거로 삼지 마세요. 당신이 돌린 결과만 근거입니다.

채점 기준도 순서가 정해져 있습니다. **1번(재현 통과)을 못 넘기면 나머지는 보지도 않습니다.**

### ⑤ 승자가 없을 수 있다

> 전부 탈락이면 **억지로 승자를 뽑지 마세요.** "승자 없음"이 정답일 수 있습니다.

경쟁 패턴이 무너지는 흔한 방식이 **셋 다 틀렸는데 그중 제일 나은 걸 고르는 것**입니다.

### ⑥ 탈락한 접근도 자산이다

최종 보고에 `## 탈락한 접근에서 배울 점` 항목이 있습니다. 세 배의 비용을 썼으니, 버린 둘에서도 뭔가는 건져야 합니다.

## `_workspace` 를 어떻게 쓰나

```
_workspace/
├── README.md              규약 (커밋됨)
├── STATUS.md              오케스트레이터의 진행판
├── 1-repro.js             ← Phase 1 산출물. 이후 모든 채점의 기준
├── 1-repro.md             재현 보고서
├── 2-candidate-a.js       ← Phase 2. 각자 자기 사본만 건드림
├── 2-candidate-a.md
├── 2-candidate-b.js
├── 2-candidate-b.md
├── 2-candidate-c.js
├── 2-candidate-c.md
├── 3-judgement.md         ← Phase 3. 채점표와 승자
└── 4-final.md             ← Phase 4. 반영 결과
```

**오케스트레이터는 파일 내용을 프롬프트에 복사하지 않습니다.** 경로만 넘깁니다.

```
task(subagent_type="judge",
     prompt="_workspace/2-candidate-*.js 를 각각 _workspace/1-repro.js 로 실제 실행해 채점하고,
             승자를 _workspace/3-judgement.md 에 쓰세요.")
```

## 직접 바꿔 보기

- **`/repro-only` 부터 돌리세요.** 재현 스크립트가 어떻게 생겼는지 보면 나머지가 이해됩니다.
- **후보 셋에게 같은 지시를 줘 보세요.** `compete-lead.md` 의 세 `접근 방향:` 을 똑같이 맞추면, 셋이 거의 같은 답을 내는 걸 볼 수 있습니다 — 경쟁이 무의미해집니다.
- **후보를 다섯으로 늘려 보세요.** 비용 대비 품질이 어디서 꺾이는지 볼 수 있습니다.
- **`judge` 모델을 저렴한 것으로 낮춰 보세요.** 실행 없이 보고서만 읽고 판정하려 드는지 확인해 보세요.
- **버그를 하나 더 심어 보세요.** `formatDuration` 에도 결함을 넣으면, 재현 스크립트가 그것까지 잡는지 볼 수 있습니다.
- **`sample/BUG.md` 의 기대값 표를 지워 보세요.** 재현 담당이 기대 동작을 스스로 정의해야 하는데, 그게 얼마나 흔들리는지 보면 **명세의 가치**를 체감할 수 있습니다.
