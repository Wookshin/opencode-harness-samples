# 02 · 전문가 풀 (Expert Pool)

> **한 줄로**: 역할별 전문가를 갖춰 두고, 요청 성격에 따라 **한 명을 골라** 쓰는 패턴.

## 바로 실행하기

```bash
cd 02-expert-pool

# 라우팅 판단만 보기 (실제 작업 안 함 — 패턴 확인용으로 이것부터 권합니다)
opencode run "/who sample/cart.js 에 테스트 좀 짜줘"

# 실제로 위임까지
opencode run "/ask sample/cart.js 에 테스트 좀 짜줘"
```

같은 파일 하나로 전문가 넷을 전부 시험할 수 있습니다.

```bash
opencode run "/ask sample/cart.js 리팩터링 해줘"           # → refactorer
opencode run "/ask sample/cart.js 주석 좀 달아줘"           # → doc-writer
opencode run "/ask 이 폴더에서 TODO 들어간 줄만 찾는 명령"  # → shell-helper
```

## 무엇을 보여주는 샘플인가

전문가 넷을 두고, 라우터가 **요청을 읽고 한 명을 고릅니다.**

| 전문가 | 맡는 일 | 모델 | 편집 권한 |
|---|---|---|---|
| `test-writer` | 단위 테스트 작성 | 무난 | 있음 |
| `refactorer` | 동작 보존 구조 개선 | 무난 | 있음 |
| `doc-writer` | 주석·README | 저렴 | 있음 |
| `shell-helper` | 셸·정규식 한 줄 | 저렴 | **없음** (실행도 안 함) |

## 패턴이 보이는 지점

### ① 라우팅 근거는 `description` 에서 나온다

각 에이전트 파일 맨 위 `description:` 을 보세요.

```yaml
description: 기존 함수에 단위 테스트를 작성합니다. "테스트 짜줘", "테스트 커버리지",
             "이 함수 검증하고 싶어" 같은 요청에 부르세요.
```

**오케스트레이터가 위임 대상을 고를 때 보는 것이 바로 이 문장입니다.** 그래서 "무엇을 하는지"뿐 아니라 **"언제 부르는지"** 를 같이 적었습니다. 트리거가 될 만한 사용자 표현을 그대로 넣어 둔 것이 요령입니다.

### ② 고른 이유를 말하게 강제했다

`pool-lead.md` 에 이렇게 돼 있습니다.

> 작업을 넘기기 **전에** 반드시 한 줄로 선언합니다.
> `이 요청은 [테스트 작성] 으로 판단했습니다 → test-writer 에게 맡깁니다.`

라우팅을 **말로 뱉게** 하면 판단이 고정되고, 잘못 골랐을 때 사람이 바로 알아챌 수 있습니다.

### ③ 각 전문가에게 "하지 않는 일"이 있다

전문가 풀이 무너지는 가장 흔한 방식은 **역할 침범**입니다. 그래서 넷 다 금지 항목을 명시했습니다.

- `test-writer` — 버그를 발견해도 **고치지 않고** 실패하는 테스트로 드러내기만
- `refactorer` — **버그 수정 금지**. 리팩터링과 수정을 섞으면 원인을 알 수 없게 되므로
- `doc-writer` — **코드 로직 수정 금지**
- `shell-helper` — 명령을 **만들기만** 하고 실행 안 함 (`bash: deny` 로 물리적으로도 차단)

### ④ 권한으로도 잠갔다

`shell-helper.md` 의 프론트매터:

```yaml
permission:
  edit: deny
  bash: deny
```

(`edit` 키 하나가 `write`·`edit`·`apply_patch` 를 모두 막습니다.)

"실행하지 마세요"라고 **쓰기만** 하면 모델이 급할 때 무시할 수 있습니다. 권한으로 닫으면 시도 자체가 막힙니다. 프롬프트와 권한을 **둘 다** 거는 게 요령입니다.

### ⑤ 한 명만 부른다

이 샘플은 의도적으로 **선택** 패턴입니다. 여러 명을 동시에 부르는 것은 팬아웃이고, `04-fanout-fanin` 에서 다룹니다.

## 직접 바꿔 보기

- **`/who` 로 먼저 돌려 보세요.** 실제 작업 없이 라우팅 판단만 보여 줍니다. 여러 요청을 넣어 보며 어떤 표현이 어디로 가는지 감을 잡기 좋습니다.
- **`description` 을 고쳐 보세요.** 예를 들어 `refactorer` 의 설명에서 "정리"라는 단어를 빼면 "코드 정리해줘"가 어디로 가는지 바뀝니다. **정의를 고치면 라우팅이 따라온다**는 것이 이 패턴의 핵심입니다.
- **`@test-writer sample/cart.js 테스트 짜줘`** 처럼 직접 지목해 보세요. 라우터를 건너뛰고 수동으로 부르는 방법입니다.
- **애매한 요청을 던져 보세요.** 예: `"sample/cart.js 좀 어떻게 해줘"` — 라우터가 물어보는지 아니면 멋대로 고르는지 확인해 보세요.
- **전문가를 하나 추가해 보세요.** 예: `perf-analyzer.md` (성능 분석, `edit: deny`). 파일 하나 추가하면 라우터 프롬프트의 매핑 표에도 한 줄 넣어 줘야 합니다 — 이 **이중 관리**가 전문가 풀의 약점입니다.

## 파일 구조

```
02-expert-pool/
├── opencode.jsonc
├── .opencode/
│   ├── agents/
│   │   ├── pool-lead.md        라우터 (primary) ← 매핑 표가 여기 있습니다
│   │   ├── test-writer.md      전문가 (무난)
│   │   ├── refactorer.md       전문가 (무난)
│   │   ├── doc-writer.md       전문가 (저렴)
│   │   └── shell-helper.md     전문가 (저렴, 권한 전면 차단)
│   └── commands/
│       ├── ask.md              /ask  — 라우팅 + 실제 위임
│       └── who.md              /who  — 라우팅 판단만
└── sample/
    └── cart.js                 테스트도 주석도 없는 지저분한 함수
```
