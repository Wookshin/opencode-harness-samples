# 구조 · 가독성 · 성능 규칙 (WPF)

`refac-design` 리뷰어가 대조하는 **유일한 기준**입니다.
여기 없는 것을 규칙이라고 제안하면 검증에서 `V-3` 으로 반려됩니다.

이 관점은 **가장 크게 말하는 자리**입니다. 그래서 가장 조심해야 합니다.
구조를 바꾸자는 말은 비용이 크고, 근거가 약하면 회의가 통째로 구조 논쟁이 됩니다.

> **이 코드베이스는 코드비하인드 방식을 씁니다.**
> "MVVM 으로 바꾸자"는 그 자체로는 제안이 되지 않습니다. 아래 `A-*` 중 하나에
> 걸리는 **구체적인 문제**를 짚고, 그 문제를 푸는 최소한의 변경을 제안하세요.

---

## A-1 · 한 메서드가 여러 가지 일을 한다

가장 흔하고, 대개 가장 값이 큽니다.

**세는 법**: 메서드 안에서 "그리고" 로 이어지는 단계가 몇 개인가.
조회 **그리고** 검증 **그리고** 저장 **그리고** 화면 갱신이면 넷입니다.

| 신호 | |
|---|---|
| 40줄이 넘는다 | 그 자체로는 문제가 아니지만 볼 이유는 됩니다 |
| 들여쓰기가 4단 이상 | 분기와 반복이 겹쳐 있습니다 |
| 중간에 빈 줄로 단락이 나뉜다 | **그 단락이 이미 함수 이름을 갖고 있습니다** |
| 지역변수가 8개 넘는다 | 단계마다 다른 상태를 들고 다닙니다 |

제안할 때는 **나눌 조각에 이름을 붙여** 적으세요. "나누세요" 만으로는 아무도 움직이지 않습니다.

> - `List<string> GetSelectedLotIds()` — 선택 수집
> - `MoveOutResult MoveOutLots(IEnumerable<string> ids)` — 검증·저장
> - `string BuildResultMessage(MoveOutResult r)` — 메시지 조립

## A-2 · 깊은 중첩

`if` 안의 `if` 안의 `foreach`. 조기 반환(guard clause)이나 메서드 추출로 평평하게 만듭니다.

## A-3 · 반복문 안에서 DB 를 오간다

**이 코드베이스에서 성능 문제의 대부분이 여기입니다.**
다만 **아래 「합치자고 하지 마세요」를 먼저 읽으세요.** 이 규칙은 오용이 가장 많습니다.

```csharp
foreach (string lotId in targetList)
{
    // Lot 하나를 보는 데 왕복이 두 번 — 여기가 줄일 수 있는 자리입니다
    DataTable rel = Call("lotreltn.selectByFromLotId", lotId);
    DataTable inf = Call("lot.selectAll", lotId);
    if (!IsMovable(rel, inf)) { ... }
}
```

줄일 것은 **반복 자체가 아니라 한 번 도는 동안의 왕복 수**입니다.

**왕복은 세 가지 모두 셉니다** — `DPICALL`·`DPIEXEC`(mapper), `SQLEXEC`(화면이
조립한 SQL), `SET_SIMAXDATA`(Rule 시스템 백엔드 호출). 마지막 것은 **본문을 볼 수
없지만 왕복인 것은 같습니다.** 반복문 안에 있으면 그대로 지적하세요 — 다만
"그 메시지가 무엇을 하는지"는 쓰지 마세요. 아무도 읽을 수 없습니다.

### ★ 「Lot 마다 조회하는 것」을 한 번으로 합치자고 하지 마세요

**이 규칙에서 가장 자주 나오는 잘못된 제안입니다.**

MES 는 **Lot 하나하나가 판정 단위**입니다. 10건을 골랐어도 각 Lot 의 상태·이력·
자재가 다르고, 한 건이 조건에 걸리면 그 건만 막고 나머지는 진행해야 합니다.
`IN` 절 한 번으로 합치면 **어느 Lot 이 왜 걸렸는지가 사라지고**, 부분 성공을
다루지 못하게 되며, 그 사이 다른 작업자가 바꾼 상태를 놓칩니다.

그래서 **"Lot 마다 도는 조회를 한 번의 `IN` 절로 합치자"** 는 제안은
**올리지 마세요.** 이런 모양이면 전부 해당합니다.

> ~~`fn_Confirm()` 이 자식 Lot ID 마다 `lfnc_bLotCheck()` 를 부릅니다.
> 자식 Lot 10건이면 검증 왕복이 20번인데, 한 번의 `IN` 절 조회로 줄이면
> 확정 버튼 클릭 후 대기가 줄어듭니다.~~ ← **이런 것을 올리지 않습니다**

건별 검증은 **줄여야 할 낭비가 아니라 지켜야 할 업무 규칙**입니다.

### 그래도 `A-3` 으로 올릴 수 있는 것

건별 검증이라는 성격을 **그대로 두면서** 왕복만 줄이는 것이면 올립니다.

| 올려도 되는 것 | 왜 |
|---|---|
| **한 Lot 을 보는 데 조회가 2~3번** 나가는 것 | 한 번으로 합쳐도 **Lot 별 판정이 그대로**입니다 |
| 반복문 **밖에서 한 번**이면 되는 것을 안에서 부르는 것 | 공통 코드·기준 정보처럼 Lot 과 무관한 조회입니다 |
| 이미 손에 있는 값을 다시 조회하는 것 | `A-4` 와 함께 봅니다 |

> `lfnc_bLotCheck()` 가 한 Lot 에 대해 `lotreltn.selectByFromLotId` 와
> `lot.selectAll` 을 **따로** 부릅니다. 둘을 조인해 한 번에 가져오면
> **Lot 별 판정은 그대로 두고** 왕복만 절반이 됩니다.

이쪽이 팀이 실제로 받아들일 수 있는 제안입니다.

### 건수와 우선순위

제안할 때 **선택 건수의 현실적인 상한**을 함께 적으세요.
"보통 몇 건을 고르나"에 따라 `먼저`인지 `참고`인지가 갈립니다.
100건을 고르는 화면이면 `먼저`지만, 보통 2~3건이면 `참고` 입니다.

## A-4 · 같은 데이터를 두 번 조회한다

`SearchLot()` 이 이미 가져온 행을 `CheckLot()` 이 다시 조회하는 식입니다.
이미 손에 있는 `DataRow` 를 넘기면 왕복이 사라집니다.

## A-5 · UI 스레드에서 동기 I/O

DB 호출·파일 접근·네트워크가 이벤트 핸들러에서 그대로 돌면 그동안 화면이 멈춥니다.
사용자는 "프로그램이 죽었다"고 말합니다.

`await Task.Run(...)` 으로 내리되, **결과를 UI 에 되돌릴 때는 디스패처가 필요합니다.**
제안에 그 점을 빼놓지 마세요. 빼면 다음 사람이 크로스 스레드 예외를 만납니다.

## A-6 · 화면 상태가 컨트롤에만 있다

`txtLotId.Text` 를 여기저기서 직접 읽고 씁니다.
값이 지금 무엇인지 알려면 화면을 봐야 하고, 테스트할 수 없습니다.

**전면 MVVM 전환을 제안하지 마세요.** 대신 그 값이 오가는 곳이 3곳 이상일 때만,
필드나 프로퍼티 하나로 모으자고 하세요.

## A-7 · XAML 에 같은 속성이 되풀이된다

컨트롤마다 같은 `Margin` · `Style` · `Width` 가 붙어 있으면 `Style` 로 뺍니다.
→ 중복 자체는 `refac-hygiene` 의 `P-3` 과 겹칩니다. **둘 중 하나만 올리세요.**

## A-8 · 코드와 XAML 이 같은 것을 두 번 정의한다

그리드 컬럼을 `InitGridColumns()` 에도, XAML `<DataGrid.Columns>` 에도 적은 경우.
어느 쪽이 이기는지 읽는 사람이 알 수 없습니다.

**한쪽을 지우자고 하기 전에 화면이 바뀌는지 확인해야 합니다.**
확인 없이 제안하면 `다음` 이상으로 올리지 마세요.

## A-9 · 예외를 삼킨다

`catch { }` 또는 `catch (Exception) { return; }`.
실패가 조용히 지나가 화면에는 "0건 조회"로 나옵니다.

## A-10 · 매직 넘버 · 매직 스트링이 흐름을 정한다

`if (status == "WAIT")` 가 여러 곳에 있으면 상태가 하나 늘 때 빠뜨립니다.
→ 값을 모으는 것 자체는 `P-4`. **여기서는 그 값이 분기를 만들 때만** 봅니다.

## A-11 · 이벤트 구독을 해제하지 않는다

`+=` 만 있고 `-=` 가 없으면 화면을 닫아도 참조가 남아 메모리가 늘어납니다.
장시간 띄워 두는 MES 화면에서 실제로 문제가 됩니다.

## 우선순위를 붙이는 기준

구조 제안은 비용이 크므로 **효과를 말할 수 있을 때만** 올립니다.

| 우선순위 | 언제 |
|---|---|
| **먼저** | 지금 사용자가 겪고 있거나(A-3·A-5 로 화면이 멈춤), 이 구조 때문에 **다른 개선이 막혀 있을 때** |
| **다음** | 고치면 읽기가 분명히 나아지지만 지금 당장 아프지는 않을 때 |
| **참고** | 취향에 가까운 것, 또는 지금 손대면 손해가 더 큰 것 |

**"그래서 무엇이 나아지는지" 한 문장을 못 쓰면 `먼저` 가 아닙니다.** 검증에서 `V-6` 으로 강등됩니다.

## 비용을 붙이는 기준

| 비용 | 언제 |
|---|---|
| **작음** | 한 메서드 안에서 끝나고 시그니처가 안 바뀜 |
| **보통** | 메서드를 나누지만 **외부 호출부가 그대로**임 |
| **큼** | 공개 시그니처·화면 동작·DB 호출 방식이 바뀜. 테스트 없이는 확인이 어려움 |

구조 제안은 대부분 `보통` 이거나 `큼` 입니다.
**`큼` 을 두려워하지 마세요.** 대신 로드맵에서 순서를 잡을 수 있게
"무엇을 먼저 끝내면 이게 쉬워지는지"를 `영향` 칸에 적으세요.

## 하지 않는 일

- **이름은 보지 않습니다.** → `refac-convention`
- **미참조·중복 그 자체는 보지 않습니다.** → `refac-hygiene`
  (중복을 합치는 것은 저기, 책임을 나누는 것은 여기입니다)
- **SQL 본문은 보지 않습니다.** → `refac-sql`
  (반복문 안에서 **부르는 방식**은 여기, 쿼리가 **무엇을 하는지**는 저기입니다)
- **프레임워크를 갈아 치우자고 하지 않습니다.** MVVM·DI·ORM 전환은 이 리포트의 범위가 아닙니다
