# 제안 출력 형식 (네 관점 공통)

컨벤션 · 중복·미사용 · 구조 · SQL 리뷰어가 **똑같이** 지키는 형식입니다.
위임 결과는 마지막 텍스트 한 덩어리로만 올라옵니다. **형식이 어긋나면 취합할 방법이 없습니다.**

> **이 리포트는 판정이 아니라 제안입니다.** 개발자가 자기 코드를 놓고 팀과 함께
> "어디부터 손댈까"를 정하는 자료입니다.
> `잘못됐습니다` · `틀렸습니다` 대신 **`이렇게 하면 …가 나아집니다`** 로 쓰세요.

---

## 1. 제안 ID

각 리뷰어는 자기 접두사로 번호를 매깁니다. 전체에서 유일해야 합니다.

| 관점 | 접두사 | 근거로 대는 것 |
|---|---|---|
| 컨벤션 | `N` | `규칙 1-4` (naming-rules.md) |
| 중복·미사용 | `H` | `K-1` · `P-1` (hygiene-rules.md) |
| 구조 | `D` | `A-3` (design-rules.md) |
| SQL | `S` | `Q-1` (read-sql.md) · SQL 본문은 따로 `Q###` |

## 2. 두 축 — 우선순위와 비용

리팩토링 제안에서 팀이 실제로 묻는 것은 하나입니다. **"그래서 뭐부터 해요?"**
그 답이 나오려면 축이 둘 필요합니다.

| 우선순위 | 뜻 |
|---|---|
| **먼저** | 지금 손대면 효과가 크거나, 이것 때문에 다른 개선이 막혀 있는 것 |
| **다음** | 해두면 좋지만 급하지 않은 것 |
| **참고** | 알아 두면 좋은 것, 취향, 지금은 두는 게 나은 것 |

| 비용 | 뜻 |
|---|---|
| **작음** | 한 파일 안에서 끝나고 되돌리기 쉬움 |
| **보통** | 여러 곳을 고치지만 대상 경로 안 |
| **큼** | 공개 시그니처·화면 동작이 바뀌거나, 경로 밖 영향 조사가 필요 |

리포트는 **`먼저 · 비용 작음`** 을 한 번에 모아 보여 줍니다. 그게 팀이 이번 주에 할 일입니다.
그러니 이 두 칸을 성의 없이 채우면 리포트의 값이 절반으로 떨어집니다.

**`먼저` 를 남발하지 마세요.** "그래서 무엇이 나아지는지" 한 문장을 못 쓰면 `다음` 입니다.
검증에서 `V-6` 으로 강등됩니다.

**`비용: 작음` 은 세어서 적을 때만** 씁니다. 영향 범위를 세지 않으면 `V-7` 로 `보통` 이 됩니다.

## 3. 대상 단위 ID 를 반드시 붙인다

`<작업폴더>/1-units.md` 의 `U1`, `U2` … 를 씁니다.
**표에 없는 심볼은 제안 대상이 아닙니다.** 인용하면 검증에서 `V-1` 로 반려됩니다.

범위 밖에 꼭 할 말이 있으면 `## 범위 밖에서 본 것` 에 적으세요. 거기는 반려되지 않습니다.

## 4. 산출물 형식

자기 파일(`<작업폴더>/2-suggest-<관점>.md` — 작업 폴더는 오케스트레이터가 알려줍니다)에
**이 형식 그대로** 씁니다.

````markdown
# <관점> 제안

## 요약

| 우선순위 | 건수 |
|---|---|
| 먼저 | 2 |
| 다음 | 3 |
| 참고 | 1 |

즉시 착수 후보(먼저 · 비용 작음): 1건

## 제안

### N001 · 먼저 · 비용 보통 · U4 · YOEDSMOV.xaml.cs:138 — `bool` 을 돌려주는 `CheckLot` 이 `Is` 로 시작하지 않고, 이름이 동작과 반대다

**무엇을**
이름은 "Lot 을 검사한다" 인데 본문은 WAIT·HELD 일 때 `true` 를 돌려줍니다.
호출부가 `if (!CheckLot(lotId))` 로 쓰고 있어, 읽는 사람과 실제 동작이 어긋납니다.

**근거**
규칙 1-4 (bool 반환은 `Is` 로 시작) · 규칙 1-2 (동작과 같은 방향의 이름)

**지금**
```csharp
private bool CheckLot(string lotId)
{
    return status == "WAIT" || status == "HELD";
}
```

**이렇게**
```csharp
private bool IsMovableLot(string lotId)
{
    return status != "WAIT" && status != "HELD";
}
```

**영향**
호출부 1곳(`Confirm()` 163줄). 반환 조건을 뒤집으면 그 자리의 `!` 도 함께 빠집니다.

**점검**
이름과 조건을 **한 커밋에서 같이** 바꾸세요. 이름만 바꾸면 반대 의미가 그대로 남습니다.

---

### N002 · 다음 · 비용 작음 · U2 · YOEDSMOV.xaml.cs:104 — (한 줄 제목)
…
````

각 절의 규칙:

| 절 | 필수 | 내용 |
|---|---|---|
| 제목줄 `### ID · 우선순위 · 비용 · 단위 · 파일:줄 — 한 줄 제목` | **필수** | 여섯 개가 다 있어야 합니다 |
| `**무엇을**` | **필수** | `먼저` 면 "그래서 무엇이 나아지는지"를 반드시 포함 |
| `**근거**` | **필수** | 규칙 번호(`규칙 1-4` · `K-1` · `A-3` · `Q-1`). 없으면 `V-3` 반려 |
| `**지금**` | **필수** | `src/` 원문과 **글자 그대로** 일치해야 합니다. 다르면 `V-2` 반려 |
| `**이렇게**` | **필수** | 코드 또는 문장. 리포트가 알아서 구분해 그립니다 |
| `**영향**` | **필수** | 이 제안이 닿는 곳. **세어서** 적습니다 — `비용` 의 근거입니다 |
| `**점검**` | 선택 | 같이 봐야 할 것, 다른 제안과의 순서 |

### `**지금**` 은 옮겨 적는 칸이 아닙니다

리포트에 실리는 코드는 `build-report.py` 가 `src/` 원문에서 **직접 잘라** 씁니다.
당신이 적는 `**지금**` 은 **어느 자리인지 가리키는 용도**입니다.
그래서 짧게, 그리고 원문과 **글자 그대로** 같게 적으세요. 다르면 `V-2` 로 반려됩니다.

길면 앞뒤를 `...` 로 줄여도 됩니다. 인용한 줄만 원문과 맞으면 됩니다.

### `**이렇게**` 는 유일하게 지어내는 칸입니다

제안 코드는 원문에 없으므로 여기서 만들 수밖에 없습니다.
리포트가 이 칸을 **「제안」으로 따로 표시**해 원문과 섞이지 않게 그립니다.

컴파일되는 코드일 필요는 없습니다. **무엇을 어떻게 바꾸는지 보이면 됩니다.**
문장으로 쓰는 편이 나은 것은 문장으로 쓰세요 — 억지로 코드로 만들면 오히려 안 읽힙니다.

## 5. 제목 한 줄이 리포트의 얼굴입니다

팀원이 실제로 읽는 것은 **제안 카드의 제목 한 줄**입니다.
목차에도, 대상 요약 표에도, 카드 머리에도 그 줄이 섭니다.

| | |
|---|---|
| **문제 자체를 씁니다** | `` `SearchLotByLine()` 이 `SearchLot()` 의 복사본이고, 부르는 곳도 없다 `` |
| **식별자는 백틱으로** | 함수·변수·컬럼·SQL ID 를 `` ` `` 로 감싸면 리포트에서 코드 칩이 됩니다 |
| 위치나 분류를 쓰지 않습니다 | ~~`SqlManager.cs 문제`~~ ~~`네이밍 규칙 위반`~~ ~~`리팩토링 필요`~~ |
| 40자 안팎, 한 줄로 | 줄바꿈 없이 |
| 읽고 바로 판단이 서게 | 제목만 보고 "이건 이번 주에 / 이건 나중에"가 갈려야 합니다 |

**나쁜 제목**: `CheckLot 함수 개선 필요` — 무엇을 개선하는지 알 수 없어 결국 본문을 읽어야 합니다.
**좋은 제목**: `` `bool` 을 돌려주는 `CheckLot` 이 `Is` 로 시작하지 않고, 이름이 동작과 반대다 ``

본문·근거·영향에서도 식별자는 백틱으로 감싸세요.
한글 문장에 코드 이름이 맨몸으로 섞이면 눈이 미끄러집니다.

## 6. 손대기 쉬운 것은 묶어서 한 줄

미사용 `using` 삭제, 변수명 하나 바꾸기처럼 **판단이 필요 없는 것**은
개별 제안으로 만들지 말고 마지막에 묶습니다. 이상점이 있을 때만 개별 제안으로 올립니다.

```markdown
## 손대기 쉬운 것

| 단위 | 내용 | 비고 |
|---|---|---|
| U7 | 미사용 `using System.Web;` 삭제 | 없음 |
| U1 | `MaxRowCount` 필드 삭제 | 없음 |
| U2 | `tmpList` → `lotIdList` (3곳) | **`SearchLotByLine()` 에도 같은 이름 — H002 와 함께** |
```

## 7. 확인 못 한 것

읽을 수 없었던 것(권한, 대상 경로 밖, 매핑 없는 mapper)은 **숨기지 말고** 적습니다.

```markdown
## 확인 못 한 것

- `SqlManager.Bind()` 가 이 경로 밖에서 쓰이는지 — 대상 경로만 훑어서 확인하지 못했습니다.
```

**이 하네스는 대상 경로만 봅니다.** `public` 멤버와 공유 mapper 에 대해서는
"이 경로 안에서는 안 쓰입니다" 까지만 말할 수 있습니다. 그 선을 넘지 마세요.

## 8. 범위 밖에서 본 것 (선택)

`1-units.md` 표 밖이지만 꼭 전할 말이 있으면 여기에 적습니다.
**이 절은 `V-1` 로 반려되지 않습니다.** 대신 리포트 본문에도 실리지 않고,
오케스트레이터가 로드맵을 쓸 때 참고합니다.

## 9. 오케스트레이터에게 돌려줄 말

파일에 다 썼으므로 **내용을 다시 옮겨 적지 마세요.** 이것만 돌려줍니다.

```
## <관점> 제안 완료

- 산출물: <작업폴더>/2-suggest-<관점>.md
- 먼저 N · 다음 N · 참고 N  (즉시 착수 후보 N)
- 확인 못 한 것: N건
```

## 10. 금지

- 코드를 **고치지 마세요.** 권한으로도 막혀 있습니다. 제안만 합니다.
- 남의 관점을 제안하지 마세요. 중복이 리포트를 망칩니다.
- 자기 관점에서 할 말이 없으면 **`없음` 이 정답**입니다. 억지로 채우지 마세요.
- **인덱스에 없는 미참조·중복을 만들어 내지 마세요.** `V-4` · `V-5` 로 반려됩니다.
- 형식 밖의 인사말·총평을 붙이지 마세요. 총평은 오케스트레이터가 씁니다.
