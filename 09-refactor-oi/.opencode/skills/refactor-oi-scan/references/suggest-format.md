# 제안 출력 형식 (세 관점 공통)

컨벤션 · 중복·미사용 · 구조 리뷰어가 **똑같이** 지키는 형식입니다.
위임 결과는 마지막 텍스트 한 덩어리로만 올라옵니다. **형식이 어긋나면 취합할 방법이 없습니다.**

> **이 리포트는 판정이 아니라 제안입니다.** 개발자가 자기 코드를 놓고 팀과 함께
> "어디부터 손댈까"를 정하는 자료입니다.
> `잘못됐습니다` · `틀렸습니다` 대신 **`이렇게 하면 …가 나아집니다`** 로 쓰세요.

---

## 1. 제안 ID

각 리뷰어는 자기 접두사로 번호를 매깁니다. 전체에서 유일해야 합니다.

| 관점 | 접두사 | 근거로 대는 것 |
|---|---|---|
| 컨벤션 | `N` | `규칙 1-4` (naming-rules.md) |
| 중복·미사용 | `H` | `K-1` · `P-1` (hygiene-rules.md) |
| 구조 | `D` | `A-3` (design-rules.md) — SQL 을 **부르는 방식**도 여기 |

## 2. 두 축 — 개선 유형과 비용

**이 리포트는 순서를 정해 주지 않습니다.** 개발자가 보고 스스로 고릅니다.
그래서 "무엇이 급한가"가 아니라 **"무엇을 바꾸는 변경인가"** 로 분류합니다.

| 개선 유형 | 무엇을 바꾸나 | 어느 규칙에서 나오나 |
|---|---|---|
| **이름 변경** | 함수·VO·변수·상수 이름 | `규칙 1-x` · `2-1` · `3-x` · `4-x` · `5-x` |
| **삭제** | 안 쓰는 멤버·변수·`using` 을 지움 | `K-1` ~ `K-4` |
| **중복 통합** | 같은 코드·같은 XAML 을 하나로 | `P-1` · `P-2` · `A-7` · `A-8` |
| **함수 추출** | 긴 메서드를 이름 붙인 조각으로 나눔 | `A-1` |
| **흐름 정리** | 중첩·조기 반환·예외 처리·구독 해제 | `A-2` · `A-6` · `A-9` · `A-11` |
| **호출 방식** | DB 왕복·비동기·SQL 을 부르는 방식 | `A-3` · `A-4` · `A-5` · `A-12` · `A-13` |
| **상수화** | 흩어진 리터럴을 `const`·`enum` 으로 | `P-3` · `A-10` |
| **SqlManager 이관** | 화면이 들고 있던 DB 통신을 `SqlManager` + VO 로 | `A-14` |

여덟 중 **정확히 하나**를 고릅니다. 둘에 걸치면 **제안이 두 개여야 한다는
신호**입니다 — 쪼개세요.

> **`함수 추출` 과 `SqlManager 이관` 은 통신으로 가릅니다.** 떼어 낼 조각 안에
> `DPICALL`·`SQLEXEC` 통신이 있으면 `SqlManager 이관` 입니다 — 함수로 묶는 것과
> 옮기는 것이 한 묶음이라, 묶기만 하고 화면에 두면 절반만 한 것입니다.

| 비용 | 뜻 |
|---|---|
| **작음** | 한 파일 안에서 끝나고 되돌리기 쉬움 |
| **보통** | 여러 곳을 고치지만 대상 경로 안 |
| **큼** | 공개 시그니처·화면 동작이 바뀌거나, 경로 밖 영향 조사가 필요 |

리포트는 이 둘로 필터를 겁니다 — **"이번엔 이름만 몰아서"** 나
**"지금 바로 할 수 있는 것(비용 작음)"** 처럼 고를 수 있게.

**`비용: 작음` 은 세어서 적을 때만** 씁니다. 영향 범위를 세지 않으면 `V-6` 로 `보통` 이 됩니다.

## 3. 대상 단위 ID 를 반드시 붙인다

`<작업폴더>/1-units.md` 의 `U1`, `U2` … 를 씁니다.
**표에 없는 심볼은 제안 대상이 아닙니다.** 인용하면 검증에서 `V-1` 로 반려됩니다.

범위 밖에 꼭 할 말이 있으면 `## 범위 밖에서 본 것` 에 적으세요. 거기는 반려되지 않습니다.

## 4. 산출물 형식

자기 파일(`<작업폴더>/2-suggest-<관점>.md` — 작업 폴더는 오케스트레이터가 알려줍니다)에
**이 형식 그대로** 씁니다.

````markdown
# <관점> 제안

## 요약

| 개선 유형 | 건수 |
|---|---|
| 이름 변경 | 2 |
| 삭제 | 3 |
| 호출 방식 | 1 |

지금 바로 할 수 있는 것(비용 작음): 1건

## 제안

### N001 · 이름 변경 · 비용 보통 · U4 · YOEDSMOV.xaml.cs:138 — `bool` 을 돌려주는 `CheckLot` 이 `Is` 로 시작하지 않고, 이름이 동작과 반대다

**왜 바꾸나**
이름은 "Lot 을 검사한다" 인데 본문은 WAIT·HELD 일 때 `true` 를 돌려줍니다.
호출부가 `if (!CheckLot(lotId))` 로 쓰고 있어, 읽는 사람과 실제 동작이 어긋납니다.

**근거**
규칙 1-4 (bool 반환은 `Is` 로 시작) · 규칙 1-2 (동작과 같은 방향의 이름)

**지금 코드** `138–148`
```csharp
private bool CheckLot(string lotId)
{
    return status == "WAIT" || status == "HELD";
}
```

**제안 코드**
```csharp IsMovableLot(string lotId)
private bool IsMovableLot(string lotId)
{
    return status != "WAIT" && status != "HELD";
}
```

**영향**
호출부 1곳(`Confirm()` 163줄). 반환 조건을 뒤집으면 그 자리의 `!` 도 함께 빠집니다.

**점검**
이름과 조건을 **한 커밋에서 같이** 바꾸세요. 이름만 바꾸면 반대 의미가 그대로 남습니다.

---

### N002 · 삭제 · 비용 작음 · U2 · YOEDSMOV.xaml.cs:104 — (한 줄 제목)
…
````

각 절의 규칙:

| 절 | 필수 | 내용 |
|---|---|---|
| 제목줄 `### ID · 개선 유형 · 비용 · 단위 · 파일:줄 — 한 줄 제목` | **필수** | 여섯 개가 다 있어야 합니다 |
| `**왜 바꾸나**` | **필수** | **"그래서 무엇이 나아지는지"를 반드시 포함** — 이것 없이는 고를 수 없습니다 |
| `**근거**` | **필수** | 규칙 번호(`규칙 1-4` · `K-1` · `A-3`). 없으면 `V-3` 반려 |
| `**지금 코드**` | **필수** | **줄 범위를 먼저 적고**, 코드는 `src/` 원문과 글자 그대로. 다르면 `V-2` 반려 |
| `**제안 코드**` | **필수** | 코드는 ``` 펜스 안에, 설명은 펜스 밖에. 리포트가 각각 제 모양으로 그립니다 |
| `**영향**` | **필수** | 이 제안이 닿는 곳. **세어서** 적습니다 — `비용` 의 근거입니다 |
| `**점검**` | 선택 | 같이 봐야 할 것, 다른 제안과의 순서 |

### `**지금 코드**` 은 옮겨 적는 칸이 아니라 **좌표**입니다

리포트에 실리는 코드는 `build-report.py` 가 `src/` 원문에서 **직접 잘라** 씁니다.
그러니 절 이름 뒤에 **줄 범위를 먼저 적으세요.** 떨어져 있으면 여러 개 적습니다.

```markdown
**지금 코드** `1233–1240` · `1250–1256`
```

붙이는 코드는 **검증용**입니다 — 그 좌표에 정말 그 코드가 있는지 `V-2` 가 대조합니다.
그래서 짧게, 원문과 **글자 그대로** 같게. 길면 앞뒤를 `...` 로 줄여도 되고,
인용한 줄만 맞으면 됩니다.

**범위를 메서드 전체로 잡지 마세요.** 전부 강조되면 아무것도 가리키지 못합니다.
64줄짜리 `Confirm()` 을 쪼개는 제안이라면 `Confirm()` 전체가 아니라
**떼어 낼 덩어리마다** 범위를 적습니다 — `152–164` · `166–199` · `201–206`.

### `**제안 코드**` 는 유일하게 지어내는 칸입니다

제안 코드는 원문에 없으므로 여기서 만들 수밖에 없습니다.
리포트가 이 칸을 **「제안」으로 따로 표시**해 원문과 섞이지 않게 그립니다.

**코드는 반드시 ``` 펜스 안에 넣으세요.** 펜스 밖 문장은 산문으로, 펜스 안은
접이식 코드 블록 + **복사 버튼**으로 그려집니다. 섞어 써도 각각 제 모양이 됩니다.
펜스를 안 치면 한글 설명까지 모노스페이스로 늘어섭니다.

펜스 머리의 언어 뒤에 **제목**을 붙이면 그것이 접이식 제목이 됩니다.

````markdown
```csharp BuildSplitParams(int row) — 671–819 줄이 들어갑니다
private Dictionary<string, string> BuildSplitParams(int row)
{
    ...
}
```
````

#### 덩어리를 옮기는 제안은 **붙여넣을 수 있는 코드**까지 씁니다

`함수 추출` · `SqlManager 이관` · `중복 통합` 은 **"어디를 어떻게 떼어내나"가 본론**입니다.
`"BuildSplitParams() 로 파라미터 조립을 떼어냅니다"` 한 줄로는 아무도 못 옮깁니다.
이 셋은 펜스를 **두 갈래로** 답니다.

| 펜스 | 무엇 |
|---|---|
| **호출부** | 떼어 낸 뒤 원래 자리에 남는 모습. 대개 두세 줄입니다 |
| **떼어 낸 함수마다 하나씩** | 본문 전체. 그대로 붙여넣어 컴파일이 시도될 만큼 |

읽는 사람이 **펴서 복사 버튼을 누르고 바로 붙이는 것**이 목표입니다.
`design-rules.md` 의 `A-1`·`A-14` 예시가 그 형태입니다.

나머지 다섯 유형(`이름 변경` · `삭제` · `흐름 정리` · `호출 방식` · `상수화`)은
지금처럼 **문장이 나은 것은 문장으로** 쓰세요. 억지로 코드로 만들면 오히려 안 읽힙니다.

### 파일은 **먼저 만들고 이어 씁니다**

**아무것도 읽기 전에** `# <관점> 제안` 과 `## 제안` 만 있는 **빈 파일부터 만드세요.**
그리고 제안 하나를 다 쓸 때마다 **그 자리에서 파일에 붙입니다.**

읽기가 가장 긴 구간입니다. 「읽기를 마치고 쓰자」 로 미루면, **읽다가 끊겼을 때
뼈대조차 안 남아** 오케스트레이터에게는 일을 아예 안 한 것으로 보입니다.
빈 파일 하나가 「나는 시작했다」는 증거입니다.

전부 검토한 뒤 마지막에 한 번에 쓰면, 중간에 끊겼을 때 **아무것도 남지 않습니다.**
볼 규칙이 많은 관점(구조는 `A-1`~`A-14`)에서 실제로 자주 일어납니다.
이어 쓰면 끊겨도 거기까지는 남고, 오케스트레이터가 **이어서** 부를 수 있습니다 —
처음부터 다시 하지 않아도 됩니다.

### 큰 대상은 **스스로 끊습니다**

한 번에 다 보려고 하지 마세요. 대상이 복잡하면 **다 보기 전에 끊깁니다** —
그러면 돌려줄 말도, 완료 표시도 없이 끝나 오케스트레이터가 판단할 근거가 없습니다.

그래서 **당신이 먼저 끊습니다.** 파일 맨 위, 제목 바로 아래에 진행 표시를 한 줄 둡니다.

```markdown
# 구조 제안

<!-- 진행: 단위 U1–U6 까지 · 규칙 A-1–A-14 -->
```

| 언제 | 무엇을 |
|---|---|
| 단위 **예닐곱 개**를 보았고 아직 남았다 | 진행 표시를 갱신하고 **거기서 마칩니다.** `## 확인 못 한 것` 은 붙이지 않습니다 |
| 끝까지 보았다 | 진행 표시를 갱신하고 `## 요약` 을 맞춘 뒤 `## 확인 못 한 것` 을 붙입니다 |

끊고 마치는 것은 **실패가 아닙니다.** 오케스트레이터가
`ws.py --suggest-status` 로 진행을 읽어 **이어서** 부릅니다.
진행이 있는 한 계속 이어 부르므로, 남은 단위는 다음 회차에서 봅니다.

돌려줄 말에도 한 줄 적으세요 — `남은 단위: U7–U12`.

### `## 확인 못 한 것` 이 「다 썼다」는 표시입니다

절 순서는 이렇습니다. **마지막은 언제나 `## 확인 못 한 것`** 입니다.

```
# <관점> 제안
## 요약
## 제안
## 손대기 쉬운 것      (선택)
## 확인 못 한 것        ← 여기까지 있어야 완성입니다
## 범위 밖에서 본 것    (선택)
```

오케스트레이터는 **이 절이 없으면 쓰다 끊긴 파일로 봅니다.**
확인 못 한 것이 없으면 `없음` 이라고 적으세요 — 절 자체를 빼지 마세요.

**다 쓰기 전에는 이 절을 붙이지 마세요.** 먼저 붙여 두면 끊겨도 완성으로 보여,
반쪽짜리 결과가 그대로 리포트에 실립니다.

### 이어 쓰라는 말과 함께 불렸다면

`이어서 쓰세요` 라는 말을 들었다면 **이미 당신 파일에 쓴 것이 있습니다.**

1. `read` 로 그 파일을 **먼저 읽으세요.** 지우거나 덮어쓰지 않습니다.
2. 마지막 제안 ID 다음 번호부터 **이어서** 붙입니다. 이미 쓴 제안은 다시 쓰지 않습니다.
3. 아직 안 본 규칙만 봅니다. 다 보았으면 `## 요약` 표를 맞추고
   `## 확인 못 한 것` 을 붙여 마칩니다.

### 제안이 하나도 없어도 파일은 씁니다

**이것이 이 형식에서 가장 자주 어긋나는 곳입니다.**

자기 관점에서 올릴 것이 없다는 결론은 정당합니다. 하지만 그 결론을
**채팅으로만 말하고 파일을 안 쓰면, 오케스트레이터에게는 「빈 결과」로 보입니다.**
오케스트레이터는 당신이 실패했다고 판단해 같은 일을 다시 시킵니다 —
모델 호출이 두 번, 세 번 낭비되고, 그래도 파일은 끝내 생기지 않습니다.

**파일이 없는 것과 「없음」이라고 쓰인 파일은 전혀 다릅니다.**
앞은 실패이고, 뒤는 결론입니다.

그러니 **읽기를 마쳤으면 무슨 일이 있어도 자기 파일을 먼저 쓰세요.**
올릴 것이 없으면 이렇게 씁니다.

```markdown
# <관점> 제안

## 요약

| 개선 유형 | 건수 |
|---|---|
| (없음) | 0 |

지금 바로 할 수 있는 것(비용 작음): 0건

## 제안

없음 — <왜 없는지 한두 줄. 무엇을 보고 그렇게 판단했는지까지>

## 확인 못 한 것

- (있으면 적습니다. 없으면 「없음」)
```

**제안이 적은 것은 흠이 아닙니다.** 억지로 채운 제안이 회의를 망칩니다.

## 5. 제목 한 줄이 리포트의 얼굴입니다

읽는 사람이 실제로 보는 것은 **제안 카드의 제목 한 줄**입니다.
목차에도, 대상 요약 표에도, 카드 머리에도 그 줄이 섭니다.

**그리고 리포트 맨 위 「개선 제안 한눈에 보기」 표의 「무엇이 바뀌나」 칸이
바로 이 제목입니다.** 개발자는 그 표를 훑으며 무엇을 고칠지 고릅니다 —
**이 한 줄만 보고 고칠지 말지가 갈립니다.** 본문을 열게 만드는 제목은
그 자리에서 건너뛰어집니다.

| | |
|---|---|

## 7. 확인 못 한 것

읽을 수 없었던 것(권한, 대상 경로 밖, 매핑 없는 mapper)은 **숨기지 말고** 적습니다.

```markdown
## 확인 못 한 것

- `SqlManager.Bind()` 가 이 경로 밖에서 쓰이는지 — 대상 경로만 훑어서 확인하지 못했습니다.
```

**이 하네스는 대상 경로만 봅니다.** `public` 멤버와 공유 mapper 에 대해서는
"이 경로 안에서는 안 쓰입니다" 까지만 말할 수 있습니다. 그 선을 넘지 마세요.

## 10. 금지

- **파일을 쓰지 않은 채 끝내지 마세요.** 올릴 것이 없어도 「없음」으로 씁니다.
  파일이 없으면 오케스트레이터에게는 실패로 보이고, 같은 일을 다시 시킵니다.
- **다 쓰기 전에 `## 확인 못 한 것` 을 붙이지 마세요.** 그 절이 「완성」 표시입니다.
- 이어 쓰라고 불렸는데 **처음부터 다시 쓰지 마세요.** 또 끊깁니다.
- **진행 표시(`<!-- 진행: … -->`)를 지우지 마세요.** 오케스트레이터가 그 줄을 읽어
  어디부터 이어 부를지 정합니다. 없으면 처음부터 다시 시킵니다.
- 코드를 **고치지 마세요.** 권한으로도 막혀 있습니다. 제안만 합니다.
- 남의 관점을 제안하지 마세요. 중복이 리포트를 망칩니다.
- 자기 관점에서 할 말이 없으면 **`없음` 이 정답**입니다. 억지로 채우지 마세요.
- **인덱스에 없는 미참조·중복을 만들어 내지 마세요.** `V-4` · `V-5` 로 반려됩니다.
- 형식 밖의 인사말·총평을 붙이지 마세요. 총평은 오케스트레이터가 씁니다.
