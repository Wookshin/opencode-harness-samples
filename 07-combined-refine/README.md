# 07 · 조합 · 반복 정제형 (Refine)

> **한 줄로**: 한 번에 잘 만들려 하지 않고, **조사 → 집필 → 빈틈 지적 → 그 빈틈만 재조사** 를 반복해 수렴시키는 조합.

## 바로 실행하기

```bash
cd 07-combined-refine

# 라운드 1만 (권장 — 반복 구조를 보려면 이것부터)
opencode run "/round-one"

# 전체 — 판정이 DONE 이 될 때까지, 최대 3라운드
opencode run "/document"

# 라운드가 어떻게 진행됐는지
opencode run "/status"
```

결과물은 `_workspace/FINAL.md` 에 나옵니다.

## 무엇을 보여주는 샘플인가

`sample/` 에 **noteq** 라는 작은 메모 큐 CLI가 있습니다(파일 3개). 이것의 **사용 문서를 만드는** 것이 과제입니다.

문서화는 반복 정제 패턴이 잘 드러나는 작업입니다. 한 번에 다 쓰려 하면 반드시 빠지는 게 생기고, 무엇이 빠졌는지는 **써 보고 나서야** 알 수 있기 때문입니다.

## 조합된 패턴

| Phase | 담당 | 패턴 | 모델 |
|---|---|---|---|
| A 조사 | `scout-agent` ×2~4 | **팬아웃** — 주제를 나눠 동시 조사 | 저렴 |
| B 집필 | `writer` | **파이프라인** — 조사 결과를 문서로 | 무난 |
| C 감사 | `gap-auditor` | **생성-검증** — 빈틈을 찾아 판정 | **고가** |
| ↻ | | **반복** — CONTINUE 면 다시 A로 | |

## 패턴이 보이는 지점

### ① 매 라운드가 **좁아진다**

이게 이 패턴의 전부입니다.

- **라운드 1** — 넓게 훑습니다. 구조·사용법·설정 같은 큰 주제 3~4개.
- **라운드 2 이상** — `gaps.md` 가 지목한 **그 항목만** 팝니다.

`refine-lead.md`:

> 라운드 2 이상에서 **전체를 다시 조사시키지 마세요.** 지적된 항목만입니다.

전체를 다시 돌리면 비용만 3배 들고 같은 결과가 나옵니다.

### ② 감사관이 **다음 라운드의 배정표**를 만든다

`gap-auditor.md` 의 산출물에는 지적만 있는 게 아니라 이런 표가 들어 있습니다.

```markdown
## 다음 라운드 조사 항목

| # | 주제 | 무엇을 알아내야 하는가 |
|---|---|---|
| 1 | 오류 처리 | 어떤 오류가 나고 각각 어떻게 대응하는지 |
```

> 지적으로 끝내지 말고, **다음 라운드에 누가 무엇을 조사해야 하는지**를 구체적으로 지정하세요.

이 표가 그대로 다음 라운드 조사원들의 프롬프트가 됩니다. **검증자가 다음 사이클의 입력을 만드는 것** — 루프가 스스로 돌아가게 하는 장치입니다.

### ③ 가장 비싼 모델이 감사관에게 간다

```yaml
# gap-auditor
model: codemate/CodeLLMMax
```

> 이 샘플에서 가장 비싼 모델을 쓰는 자리입니다. **여기서 놓치면 다음 라운드가 통째로 헛돕니다.**

조사와 집필은 다시 할 수 있지만, **빈틈을 못 찾으면 그 라운드 전체가 낭비**됩니다.

### ④ 감사관은 원고만 읽지 않는다

> **원고만 읽고 판정하지 마세요.** 실제 코드와 대조해야 BLOCKER를 잡을 수 있습니다.

원고와 조사 결과만 비교하면 **조사 단계에서 이미 틀린 것**은 영영 못 잡습니다. 그래서 감사관에게 코드 읽기 권한을 줍니다.

### ⑤ 추측 금지가 3중으로 걸려 있다

| 담당 | 규칙 |
|---|---|
| 조사원 | 확인 못 한 것은 `(확인 못 함)` 이라고 명시. 추측으로 메우지 않음 |
| 집필자 | **조사 결과에 없는 내용을 쓰지 않음.** `(확인 못 함)` 을 채워 넣지 않음 |
| 감사관 | 근거 없는 단정을 `UNSUPPORTED` 로 지적 |

문서 생성에서 가장 위험한 것이 **그럴듯하게 지어낸 문장**입니다. 세 곳에서 막습니다.

### ⑥ 끝나는 조건이 있다

> **최대 3라운드.** 3라운드 후에도 `CONTINUE` 면 멈추고 사용자에게 보고합니다.
> 무한히 다듬는 것을 막는 장치입니다. 완벽한 문서보다 **끝나는 문서**가 낫습니다.

### ⑦ 개정이지 재작성이 아니다

집필자는 2회차부터 **이전 원고를 개정**합니다.

> 2회차 이상: **이전 원고를 개정합니다.** 처음부터 다시 쓰지 마세요.
> 지적된 빈틈을 메우고, 나머지는 그대로 둡니다.

매번 새로 쓰면 1라운드에서 잘 쓴 부분이 사라지고, 수렴하지 않습니다.

## `_workspace` 를 어떻게 쓰나

라운드 번호가 파일명 앞에 붙어 **이력이 그대로 남습니다.**

```
_workspace/
├── README.md                 규약 (커밋됨)
├── STATUS.md                 라운드 진행판
│
├── 1-scout-structure.md      ← 라운드 1 · 조사 (동시 3명)
├── 1-scout-usage.md
├── 1-scout-config.md
├── 1-draft.md                ← 라운드 1 · 초안
├── 1-gaps.md                 ← 라운드 1 · 감사 (판정 + 다음 조사 항목)
│
├── 2-scout-errors.md         ← 라운드 2 · 지적된 것만 재조사
├── 2-draft.md                ← 라운드 2 · 개정판
├── 2-gaps.md                 ← 라운드 2 · 감사
│
└── FINAL.md                  최종본
```

**`/status` 를 돌리면 라운드를 거치며 무엇이 고쳐졌는지** 원고들을 비교해 보여 줍니다. 파일로 남기기 때문에 가능한 일입니다.

## 직접 바꿔 보기

- **`/round-one` 을 먼저 돌리세요.** 마지막에 `1-gaps.md` 를 보여 주므로, **다음 라운드에 무엇을 조사하게 되는지**가 눈에 보입니다. 반복 구조를 이해하는 가장 빠른 길입니다.
- **`1-draft.md` 와 `2-draft.md` 를 직접 비교해 보세요.** 무엇이 늘었는지가 이 패턴의 성과입니다.
- **감사관 모델을 저렴한 것으로 낮춰 보세요.** 라운드 수가 늘거나, 반대로 빈틈을 못 찾아 일찍 `DONE` 이 나옵니다. 둘 다 나쁜 결과입니다.
- **최대 라운드를 5로 늘려 보세요.** 어느 라운드부터 개선이 멈추는지 볼 수 있습니다. 보통 2~3에서 수렴합니다.
- **조사 주제를 겹치게 줘 보세요.** `refine-lead.md` 에서 주제를 일부러 겹치게 나누면, 같은 조사를 두 번 하는 낭비를 확인할 수 있습니다.
- **`sample/lib/config.js` 에 설정을 하나 더 추가해 보세요.** 문서에 반영되기까지 몇 라운드가 걸리는지 보면, 감사관의 역할이 체감됩니다.
- **집필자의 "조사 결과에 없는 내용을 쓰지 마세요"를 지워 보세요.** 그럴듯하지만 틀린 문장이 생기고, 감사관이 `UNSUPPORTED` 로 잡아내는지 확인해 보세요.
