# 05 · 조합 (Combined)

> **한 줄로**: 앞의 네 패턴을 하나의 작업 흐름으로 엮은 것. **게이트**로 단계를 강제합니다.

## 바로 실행하기

```bash
cd 05-combined

# 계획만 세우고 멈추기 (여기부터 권합니다)
opencode run "/plan-only"

# 전체 사이클 — 계획 → 병렬 구현 → 4인 리뷰 → 최종 검증
opencode run "/feature"
```

인자를 비우면 `sample/REQUEST.md` 의 요청을 사용합니다. 직접 요청을 줄 수도 있습니다.

```bash
opencode run "/feature todo.js 에 항목 삭제 기능 추가해줘"
```

## 무엇을 보여주는 샘플인가

작은 할 일 CLI(`sample/todo.js`)에 기능 두 개를 추가합니다. 요청서는 `sample/REQUEST.md` 에 있습니다.

이 요청은 일부러 **서로 독립적인 두 기능**(완료 표시 / 통계 보기)으로 짜여 있습니다. 그래야 계획 단계에서 **병렬 실행 계획**이 자연스럽게 나옵니다.

## 네 패턴이 어디에 있나

| 단계 | 담당 | 패턴 | 모델 |
|---|---|---|---|
| 1. 계획 | `planner` | **파이프라인** — 조사 후 계획서로 인계 | 고가 |
| 2. 구현 | `implementer` ×N | **팬아웃** — 독립 작업 동시 진행 | 무난 |
| 3. 리뷰 | 리뷰어 4인 | **팬아웃-팬인** — 4개 관점 동시 → 취합 | 저렴~고가 |
| 4. 검증 | `final-verifier` | **생성-검증** — 실행해서 판정, 실패 시 되돌림 | 고가 |

## 패턴이 보이는 지점

### ① 게이트가 단계를 강제한다

`.opencode/agents/combo-lead.md` 의 핵심 세 줄:

> - **계획 없이 구현 금지** — `PLAN.md` 가 없으면 2단계로 가지 않습니다.
> - **리뷰 없이 검증 금지** — 리뷰가 FAIL 이면 4단계로 가지 않고 2단계로 되돌아갑니다.
> - **증거 없이 완료 금지** — 최종 검증의 실행 출력이 없으면 완료를 선언하지 않습니다.

조합 패턴에서 가장 흔한 실패는 **단계를 건너뛰는 것**입니다. "이건 간단하니까 계획은 생략하자"가 시작입니다. 게이트를 명시적으로 적어 두면 그 판단을 모델이 하지 않습니다.

### ② 계획서가 병렬 실행 계획을 낳는다

`planner` 는 작업 표에 **선행 작업**과 **병렬 가능** 칸을 반드시 채워야 합니다.

```markdown
| # | 작업 | 대상 파일 | 선행 작업 | 병렬 가능 |
|---|---|---|---|---|
| 1 | done 명령 추가 | todo.js | 없음 | 2와 병렬 |
| 2 | stats 명령 추가 | todo.js | 없음 | 1과 병렬 |
```

2단계 오케스트레이터는 이 표를 그대로 읽어 동시 호출 개수를 정합니다. **계획서가 실행 계획이 되는 것**이 이 패턴의 핵심입니다.

### ③ 동시 구현자에게 대상 파일을 못 박는다

> 각 구현자에게 **대상 파일을 명시**하세요. 동시에 도는 구현자끼리 같은 파일을 고치면 서로를 덮어씁니다.

병렬 구현의 가장 현실적인 위험입니다. OmO 같은 도구는 이걸 **팀원별 git worktree**로 풀지만, 이 샘플은 그런 장치가 없으므로 **범위를 프롬프트로 나눕니다.**

> 💡 이 샘플의 요청서는 두 기능 다 `todo.js` 한 파일을 건드립니다. 계획자가 이를 어떻게 처리하는지(순차로 돌리는지, 함수 단위로 나누는지) 보는 것이 관전 포인트입니다.

### ④ 권한으로 역할을 못 박았다

- `planner` — `edit` 이 **`PLAN.md` 한 파일에만** 허용됩니다. 계획자가 구현으로 넘어갈 수 없습니다.
  ```yaml
  edit:
    "*": deny
    "PLAN.md": allow
  ```
  글롭 패턴 권한의 좋은 예입니다.
- 리뷰어 4인 — `edit: deny`
- `final-verifier` — `edit: deny`, `bash: allow`
- `implementer` — 유일하게 자유롭게 편집 가능

**고칠 수 있는 사람이 딱 한 종류뿐**입니다.

### ⑤ 이 샘플만 `subagent_depth: 2` 다

`opencode.jsonc`:

```jsonc
// 기본값 1이면 "서브에이전트는 서브에이전트를 부를 수 없습니다".
// 여기서는 planner 가 조사를 위해 explore 를 부를 수 있어야 하므로 2로 올립니다.
"subagent_depth": 2,
```

`planner` 는 서브에이전트인데, 그 안에서 또 `explore` 를 부릅니다. 기본값 1에서는 **이 호출이 실패합니다.**

### ⑥ 실패는 되돌림으로 처리한다

리뷰 FAIL 이든 검증 FAIL 이든, **새 구현자를 부르지 않고** 해당 작업을 했던 구현자의 세션(`task_id`)으로 되돌립니다. 그 사람은 자기가 무엇을 했는지 기억하고 있습니다.

## 직접 바꿔 보기

- **`/plan-only` 부터 돌려 보세요.** 계획 단계만 보면 나머지가 훨씬 잘 이해됩니다. `PLAN.md` 가 어떻게 생겼는지, 병렬 계획이 어떻게 잡히는지 확인하세요.
- **`subagent_depth` 를 1로 되돌려 보세요.** `planner` 가 `explore` 를 부르는 지점에서 막힙니다. 위임 깊이 제한이 실제로 무엇을 막는지 눈으로 볼 수 있습니다.
- **`planner` 의 `edit` 권한을 `allow` 로 열어 보세요.** 계획자가 계획을 세우다 말고 직접 구현하기 시작합니다. 역할 분리가 권한으로 지켜진다는 걸 확인할 수 있습니다.
- **게이트를 하나 지워 보세요.** "리뷰 없이 검증 금지"를 지우면 리뷰가 FAIL 인데도 통과하는 경우가 생깁니다.
- **요청서를 바꿔 보세요.** `sample/REQUEST.md` 에 **서로 의존하는** 기능 두 개를 적으면(예: "우선순위 필드 추가" → "우선순위순 정렬") 계획자가 병렬이 아니라 순차로 잡는지 확인할 수 있습니다.
- **완료 기준을 빡세게 해 보세요.** `REQUEST.md` 에 "기존 `todos.json` 을 그대로 읽을 수 있어야 한다"를 넣어 두었으니, 구현자가 저장 형식을 바꾸면 최종 검증에서 잡힙니다.

## 파일 구조

```
05-combined/
├── opencode.jsonc              subagent_depth: 2 ← 이 샘플만
├── .opencode/
│   ├── agents/
│   │   ├── combo-lead.md       전체 오케스트레이터 (primary) ← 게이트가 여기
│   │   ├── planner.md          1단계 · PLAN.md 만 쓸 수 있음 (고가)
│   │   ├── implementer.md      2단계 · 유일하게 편집 가능 (무난)
│   │   ├── review-*.md         3단계 · 04에서 가져온 리뷰어 4인
│   │   └── final-verifier.md   4단계 · 실행해서 판정, 편집 불가 (고가)
│   └── commands/
│       ├── feature.md          /feature    — 전체 사이클
│       └── plan-only.md        /plan-only  — 계획만
├── sample/
│   ├── todo.js                 시작 코드 (add / list 만 있음)
│   └── REQUEST.md              추가할 기능 2개
└── PLAN.md                     (실행하면 생깁니다)
```

> **참고**: 리뷰어 4인은 `04-fanout-fanin` 에서 **복사해 온 것**입니다. OpenCode 설정은 폴더 경계를 넘어 공유되지 않으므로(각 폴더가 독립적으로 동작하도록 그렇게 설계했습니다), 재사용하려면 실제로 복사해야 합니다.
