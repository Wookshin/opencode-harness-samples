# 리뷰 출력 형식 (세 관점 공통)

리팩토링 · 기능 · SQL 리뷰어가 **똑같이** 지키는 형식입니다.
위임 결과는 마지막 텍스트 한 덩어리로만 올라옵니다. **형식이 어긋나면 취합할 방법이 없습니다.**

> **이 리뷰는 합격/불합격을 판정하지 않습니다.** 개발자가 팀원에게 자기 변경을 보여주는 자료이고,
> 당신이 쓰는 것은 "여기는 같이 봐 주세요"라는 **주의 메시지**입니다.
> `틀렸다` · `잘못됐다` 대신 `이렇게 되면 …가 생깁니다` · `확인이 필요합니다` 로 쓰세요.

---

## 1. 지적 ID

각 리뷰어는 자기 접두사로 번호를 매깁니다. 전체에서 유일해야 합니다.

| 관점 | 접두사 | 예 |
|---|---|---|
| 리팩토링 | `R` | `R001`, `R002` |
| 기능 | `F` | `F001`, `F002` |
| SQL | `S` | `S001`, `S002` |

## 2. 주의 등급

| 등급 | 언제 |
|---|---|
| **꼭 확인** | 실행하면 바로 드러날 문제. **"그래서 무슨 일이 생기는지"를 한 문장으로 쓸 수 있을 때만** |
| **확인 권장** | 지금 당장은 안 터지지만 같이 봐 두는 게 좋은 것 |
| **참고** | 알아 두면 좋은 것, 취향·개선 제안 |

`꼭 확인` 을 남발하지 마세요. 결과가 생기는 시나리오를 못 쓰면 `확인 권장` 입니다.
**검증 단계에서 시나리오 없는 `꼭 확인` 은 `확인 권장` 으로 내려갑니다.**

## 3. 변경단위 ID 를 반드시 붙인다

`<작업폴더>/1-hunks.md` 의 `L1`, `L2` … 를 씁니다.
**표에 없는 라인은 리뷰 대상이 아닙니다.** 지적하면 검증에서 `REJECTED` 됩니다.

## 4. 산출물 형식

자기 파일(`<작업폴더>/2-review-<관점>.md` — 작업 폴더는 오케스트레이터가 알려줍니다)에 **이 형식 그대로** 씁니다.

````markdown
# <관점> 리뷰

## 요약

| 등급 | 건수 |
|---|---|
| 꼭 확인 | 1 |
| 확인 권장 | 2 |
| 참고 | 4 |

## 발견

### R001 · 꼭 확인 · L2 · YOEDSMOV.xaml.cs:96 — bool 반환 함수가 Is 로 시작하지 않고, 이름이 동작과 반대다

**무엇을 봐야 하나**
bool 을 반환하는 `CheckLot` 이 유효할 때 false 를 반환합니다. 호출부 96 라인이
`if (CheckLot(lotId))` 로 쓰고 있어 유효한 Lot 이 반출에서 제외됩니다.

**근거**
규칙 1-4 (bool 반환은 Is 로 시작) / 규칙 1-2 (구체적인 이름)

**변경 전**
```csharp
private bool CheckLot(string lotId)
```

**변경 후**
```csharp
private bool CheckLot(string lotId)   // 이름은 그대로, 반환 조건만 뒤집힘
```

**개선 방향**
```csharp
private bool IsValidLotStatus(string lotId)
```

**점검 사항**
호출부 3곳(96, 142, 208)의 조건이 모두 뒤집혀야 합니다.

---

### R002 · 참고 · L5 · SqlManager.cs:41 — (한 줄 제목)
…
````

각 항목의 규칙:

| 절 | 필수 | 내용 |
|---|---|---|
| 제목줄 `### ID · 등급 · 변경단위 · 파일:라인 — 한 줄 제목` | **필수** | 다섯 개가 다 있어야 합니다. **제목이 빠지면 회의 자료의 얼굴이 비어 버립니다**(아래 참고) |
| `**무엇을 봐야 하나**` | **필수** | 꼭 확인 면 "그래서 무슨 일이 생기는지"를 반드시 포함 |
| `**근거**` | **필수** | 규칙 번호(`1-4`) 또는 체크리스트 번호(`M-1`). 없으면 REJECTED |
| `**변경 전**` | 변경일 때만 | 신규 추가면 생략 |
| `**변경 후**` | **필수** | 원문과 **글자 그대로** 일치해야 합니다 |
| `**개선 방향**` | **필수** | 코드로 제시. 말로만 적지 마세요 |
| `**점검 사항**` | 선택 | 회의에서 같이 봐야 할 것 |

## 5. 제목 한 줄이 회의 자료의 얼굴입니다

HTML 리포트의 맨 위에는 **리뷰 체크리스트**가 있습니다. 지적 전체가 심각도 순으로 한 줄씩
늘어서고, 팀원들은 **그 줄만 읽고 무엇을 볼지 정합니다.** 코드는 필요할 때만 펼칩니다.

그 한 줄이 바로 제목줄의 마지막 칸입니다. 그러니 이렇게 쓰세요.

| | |
|---|---|
| **문제 자체를 씁니다** | `` `_sql.Init()` 없이 공유 빌더에 `param` 과 SQL 을 쌓는다 `` |
| **식별자는 백틱으로** | 함수·변수·컬럼·SQL ID 를 `` ` `` 로 감싸면 리포트에서 코드 칩이 됩니다 |
| 위치나 분류를 쓰지 않습니다 | ~~`SqlManager.cs 문제`~~ ~~`네이밍 규칙 위반`~~ |
| 40자 안팎, 한 줄로 | 줄바꿈 없이 |
| 읽고 바로 판단이 서게 | 제목만 보고 "이건 급하다 / 나중에 봐도 된다"가 갈려야 합니다 |

**나쁜 제목**: `CheckLot 함수 검토 필요` — 무엇이 문제인지 알 수 없어 결국 본문을 읽어야 합니다.
**좋은 제목**: `bool 반환 함수가 Is 로 시작하지 않고, 이름이 동작과 반대다`

`**무엇을 봐야 하나**` 는 제목을 풀어 쓰는 자리이지, 제목 대신 쓰는 자리가 아닙니다.

본문·근거·점검 사항에서도 식별자는 백틱으로 감싸세요. 한글 문장에 코드 이름이 맨몸으로
섞이면 눈이 미끄러집니다.

## 6. 단순 리팩토링은 묶어서 한 줄

변수명 변경, 미사용 코드 삭제, 들여쓰기 정리처럼 **판단이 필요 없는 것**은
개별 지적으로 만들지 말고 마지막에 묶습니다. **이상점이 있을 때만** 개별 지적으로 올립니다.

```markdown
## 단순 변경 요약

| 변경단위 | 내용 | 이상점 |
|---|---|---|
| L7 | `tmpList` → `lotIdList` 로 이름 변경 (3곳) | 없음 |
| L8 | 미사용 `using System.Web;` 삭제 | 없음 |
| L9 | `_operId` → `_operatorId` 로 이름 변경 | **호출부 2곳이 안 바뀜 → R008 로 별도 지적** |
```

## 7. 확인 못 한 것

읽을 수 없었던 것(권한, 저장소 밖 파일, 매핑 없는 DPImgr)은 **숨기지 말고** 적습니다.

```markdown
## 확인 못 한 것

- `lot.selectMcLot` 본문 — dpimgr-dir.txt 에 `ZZ_SWP` 매핑이 없어 조회하지 못했습니다.
```

## 8. 오케스트레이터에게 돌려줄 말

파일에 다 썼으므로 **내용을 다시 옮겨 적지 마세요.** 이것만 돌려줍니다.

```
## <관점> 리뷰 완료

- 산출물: <작업폴더>/2-review-<관점>.md
- 꼭 확인 N · 확인 권장 N · 참고 N
- 확인 못 한 것: N건
```

## 9. 금지

- 코드를 **고치지 마세요.** 권한으로도 막혀 있습니다. 지적만 합니다.
- 남의 관점을 지적하지 마세요. 중복이 리포트를 망칩니다.
- 자기 관점에서 할 말이 없으면 **`없음` 이 정답**입니다. 억지로 채우지 마세요.
- 형식 밖의 인사말·총평을 붙이지 마세요.
