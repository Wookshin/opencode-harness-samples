# 03 · 생성-검증 (Generate-Verify)

> **한 줄로**: 만드는 쪽과 검사하는 쪽을 **권한으로 분리**하고, 실패하면 되돌려 고치게 하는 패턴.

## 바로 실행하기

```bash
cd 03-generate-verify
opencode run "/build-game"
```

`game.js` 가 만들어지고, 검증을 통과할 때까지 루프가 돕니다.

이미 만들어진 게임을 판정만 해 보려면:

```bash
opencode run "/verify-game"
```

## 무엇을 보여주는 샘플인가

숫자야구 게임을 만듭니다. 규칙은 `sample/RULES.md` 에 있고, **합격 기준 9개**가 표로 정해져 있습니다.

| 역할 | 담당 | 모델 | 편집 | bash |
|---|---|---|---|---|
| 만든다 | `game-builder` | 무난 | **가능** | 가능 |
| 판정한다 | `game-verifier` | **고가** | **불가** | 가능 |
| 굴린다 | `gv-lead` | 무난 | ask | 가능 |

## 패턴이 보이는 지점

### ① 검증자는 고칠 수 없다 — 권한으로

`.opencode/agents/game-verifier.md` 의 프론트매터:

```yaml
permission:
  edit: deny
  bash: allow
```

이 두 줄이 이 샘플의 전부라고 해도 됩니다.
(`edit` 키 하나가 `write`·`edit`·`apply_patch` 세 도구를 한꺼번에 막습니다.
 `write:` 같은 키를 따로 쓸 필요가 없고, 써도 효과가 없습니다.)

검증자가 코드를 고칠 수 있으면 무슨 일이 생기냐면 — **자기가 지적한 문제를 슬쩍 고쳐 놓고 "통과"라고 보고합니다.** 지적이 사라지고, 사람은 무엇이 문제였는지 영영 모릅니다. 회사에서 감사팀과 실무팀을 나누는 것과 정확히 같은 이유입니다.

`bash` 는 열어 뒀습니다. **읽어서 판단하는 게 아니라 실제로 돌려 봐야** 하기 때문입니다.

### ② 검증자가 더 비싼 모델을 쓴다

```yaml
# game-builder
model: codemate/CodeLLMPro     # 무난

# game-verifier
model: codemate/CodeLLMMax     # 고가
```

직관과 반대로 보이지만 의도한 것입니다. **대충 만든 것을 통과시키는 비용이, 잘 만든 것을 다시 보는 비용보다 큽니다.** 검증을 싸게 때우면 검증하는 의미가 없습니다.

### ③ 실패는 "처음부터 다시"가 아니라 "이어서"

`gv-lead.md` 의 3단계:

> **새로 시키지 마세요.** 앞서 만든 builder 의 세션으로 되돌립니다.
> `task_id` 를 그대로 넘기면 builder 는 자기가 무엇을 만들었고 무엇을 시도했는지 **기억한 채로** 이어서 고칩니다.

새 위임을 만들면 그 담당자는 파일을 처음부터 다시 읽고, 이미 해 본 시도를 또 합니다. 세션을 재개하면 그게 전부 남아 있습니다.

한편 **검증자는 매번 새로 부릅니다.** 이전 판정에 끌려가면 안 되니까요. 되돌리는 쪽과 새로 부르는 쪽이 다릅니다.

### ④ 판정에 부분 점수가 없다

`game-verifier.md`:

> 합격 기준을 **하나라도** 못 지키면 `FAIL` 입니다. 부분 점수는 없습니다.
> 애매하면 `FAIL` 입니다. 확인되지 않은 것을 통과시키지 마세요.

"대체로 잘 됩니다"를 없애는 장치입니다.

### ⑤ 근거 없는 PASS는 무효

검증자는 판정마다 **실행 출력을 근거로** 남겨야 합니다. 표의 "근거" 칸이 비어 있으면 그 판정은 읽지 않은 것입니다.

### ⑥ 기준을 자기에게 맞추는 것을 막았다

`game-builder.md`:

> `sample/RULES.md` 를 수정하지 마세요. **기준을 자기에게 맞추는 것**은 반칙입니다.
> 검증을 우회하는 코드(테스트 감지, 하드코딩된 정답)를 넣지 마세요.

### ⑦ 포기 조건이 있다

3회 연속 실패하면 멈추고 사람에게 넘깁니다. 이게 없으면 같은 실패를 무한히 반복하며 토큰을 태웁니다.

## 직접 바꿔 보기

- **검증자의 권한을 열어 보세요.** `edit: deny` → `edit: allow` 로 바꾸고 돌리면, 검증자가 문제를 발견하고는 자기가 고쳐 놓고 `PASS` 를 내는 장면을 볼 수 있습니다. **이 샘플에서 가장 인상적인 실험입니다.**
- **일부러 규칙을 깨 보세요.** `game.js` 가 만들어진 뒤 `judge` 함수의 볼 계산을 살짝 틀리게 고치고 `/verify-game` 을 돌려 보세요. 검증자가 몇 번 기준에서 잡아내는지 확인할 수 있습니다.
- **합격 기준을 하나 추가해 보세요.** `RULES.md` 표에 10번을 넣으면(예: "10회 안에 못 맞히면 정답을 알려 주고 종료") 다음 실행부터 그 기준이 검증됩니다. **기준 문서가 곧 테스트 명세**입니다.
- **`gv-lead` 의 3회 제한을 1회로 줄여 보세요.** 포기 조건이 어떻게 동작하는지 빨리 볼 수 있습니다.
- **검증자 모델을 저렴한 것으로 낮춰 보세요.** 놓치는 항목이 생기는지 비교해 보면 검증에 비싼 모델을 쓰는 이유가 체감됩니다.

```
03-generate-verify/
├── opencode.jsonc
├── .opencode/
│   ├── agents/
│   │   ├── gv-lead.md          루프 오케스트레이터 (primary)
│   │   ├── game-builder.md     만드는 쪽 (edit 가능)
│   │   └── game-verifier.md    판정하는 쪽 (edit 차단) ← 핵심
│   └── commands/
│       ├── build-game.md       /build-game   — 생성 + 검증 루프
│       └── verify-game.md      /verify-game  — 판정만
├── sample/
│   └── RULES.md                규칙 + 합격 기준 9개 + 검증 인터페이스
└── game.js                     (실행하면 생깁니다)
```
